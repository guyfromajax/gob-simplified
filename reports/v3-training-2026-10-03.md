## 4. Training playbook choice carries forward

**Before:** the choice and the custom playbook's plays lived only in the browser's `sessionStorage` and were wiped by every Submit Training. Every training started on Current Playbooks.

**Now:** a saved setting on the franchise.

| Piece | What |
|---|---|
| Storage | `franchises.training_playbook_choice = {mode: "custom", focus: {offense: [...], defense: [...]}}`. Absent = Current Playbooks. No new collection, so nothing to register in the persistence adapter. |
| Save | `PATCH /franchise/training-playbook-choice` (owner only). Custom Playbook page → Save & Continue saves `custom` + its plays before leaving. Training page → Current Playbooks saves `current-playbooks` (removes the field with `$unset`). |
| Read | `GET /franchise/training-points` (the read the training page already makes) returns `training_playbook_choice`. A saved custom choice refills the page's working copy on every load. |
| Percentages | A custom playbook's percentages are an even split over its plays (two plays = 50% each), so carrying the plays carries the percentages. |
| Across weeks, camp, seasons | The franchise document is only ever updated in place (never replaced), and no other write names this field. |
| Offline | Same route, same store call; `/franchise/...` routes follow a local franchise onto the desktop engine. Proven on the real desktop SQLite server (below). |

- Saving the choice does not run or change training: `/franchise/run-training/user` still trains with what the page submits. No sim, finalize, `cpu_week_pool` or `sim_rng` file is touched (`git diff` over `BackEnd/main.py`, `BackEnd/engine`, `BackEnd/utils/cpu_week_pool.py`, `BackEnd/utils/sim_random.py`, `game_manager.py` is empty).
- A failed save does not block the training in hand (the page's working copy still carries it).
- A saved play that no longer exists is dropped when the Custom Playbook page opens.
- **Auth/ownership is touched** (a new owner-gated route). `tests/conftest.py` overrides auth for every test, so the tests set the user explicitly and run the real `verify_franchise_owned_by_user`: another user gets 403, an anonymous call 401/403, nothing written.
