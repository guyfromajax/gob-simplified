# T1 polish — 2026-09-26

Branch `app/t1-polish`, off `develop`. Backend owns the numbers. The views render them.

## Leaders

The Per game / Totals control is gone. The view no longer sends `basis`. The API still accepts `basis=per_game|totals`; omitted `basis` is unchanged (PTS, REB, AST per game; 3PTM, BLK, STL season totals; FG% and DEF% ignore basis).

Card meta, right side:

- `PTS · per game`, `REB · per game`, `AST · per game`
- `3PTM · total`, `BLK · total`, `STL · total`
- FG% and DEF% have no right-side label

PPG, RPG, and APG stay on those heroes. 3PTM, BLK, and STL are whole numbers with no unit, in the hero and in ranks 2–5. FG% and DEF% use a `%` suffix only, at one decimal (`75.0`). `qualification_caption` is still on the season FG% and DEF% rows. The cards do not render it.

The hero portrait is `API_CONFIG.getPlayerImageUrl(playerId, { size: 'card' })`, the same call Office Player of the Game uses in `officeHome.js`. The circle stays 36px. The image is cropped with `object-fit: cover` and `object-position: 50% 22%`, the same crop as `.gob .portrait img`. No `player_id` means initials and no image. A failed load replaces the image with initials, so there is no broken-image icon. The leaders row already has `player_id`, so no image fields were added.

Position uses the roster page's source, stored in the existing `position` field (no new response field):

- A non-empty `meta.position` wins.
- Otherwise a player on the user's team uses `resolved_training_position`, then `training_position`, when that letter is PG, SG, SF, PF, or C. That is what the user's own roster shows.
- Otherwise the highest `position_ratings` entry wins. Ties keep the earlier of PG, SG, SF, PF, C. That is the read-only chip on every other roster. Training position on a CPU player is not shown.

Both the live scan and the snapshot compute that letter while the line is built. `LINE_LAYOUT` is 2, so a snapshot from before this resolution rebuilds. Lancaster's real save has no `meta.position`; Roger Henrich's hero is `Lancaster · C · SR`.

## Numbers

`GOBTables.formatOneDecimal` always prints one decimal, including the trailing `.0`. Leaders uses it for per-game values and for FG% and DEF%. Team Stats uses it for FG%, 3PT%, FT%, SCR%, and DEF%. W, L, PF, FGM, and the other counting columns stay integers.

Team Stats opens sorted by Rank ascending, and the Rank header shows that indicator. A later click still lives in the mounted view for the session.

## Offline perf

Copy of `~/Library/Application Support/GOB/local.sqlite` at `tmp/t1-offline.sqlite` (not the live file). Lancaster, 1,920 players, 128 teams. Timed `standings()` and `team_stats()` in process, plus sqlite3 for decode versus extract. The earlier browser first opens (standings 1890ms, team stats 1367ms, leaders 884ms) include the page.

Before this change, the API on that copy:

| Call | Cold | Warm |
| --- | --- | --- |
| `GET /franchise/standings` | 506ms | 302ms |
| `GET /franchise/team-stats` | 1369ms | 1188ms |

Where it went:

- The franchise document is 529KB. Fetch plus `json.loads` is about 12ms. The heavy keys are `practice_squad` (223KB) and `schedule` (130KB). `results` is 22KB. Standings is not waiting on decoding results.
- Standings cProfile: SQLite `_select` about 250ms cumulative, then deepcopy of the projected rows, the FTD team-id scan about 120ms, and the franchise `find_one` about 165ms. The standings math is small beside that.
- Team stats was a full decode of every player document (fetch about 78ms, `json.loads` about 259ms) and then a deepcopy of those documents. Aggregation itself was about 60ms.

The change is a compiled extract, the same shape as the leaders lines. SQLite team stats now `projected_tuples` of `player_id`, `meta.team_id`, and the season keys the table sums, and it reads franchise team data once instead of twice. Mongomock still uses the inclusion projection. `tests/test_team_stats_projection.py` checks the rates survive that read.

After, same process, three calls:

| Call | Times |
| --- | --- |
| standings | 621ms, 228ms, 225ms |
| team-stats | 386ms, 300ms, 368ms |

The season extract alone is 133ms. The roster read is 86ms. Aggregation is 43ms. The franchise read is 9ms. Warm standings is under 300ms. Team stats sits on that line and a cold call does not stay under it.

Not built: a week snapshot of the team-stats body, invalidated the way leaders already is (`note_season_stats_written`). A repeat open would be one document. The first open cannot get under 300ms without storing the aggregate ahead of the request, because the indexed extract plus the roster read is already about 220ms before the team-meta join. That snapshot has to be written when games finalize, which is past a projection. Standings cold time is the schedule and FTD copy, and the same kind of snapshot would be the next step there too.
