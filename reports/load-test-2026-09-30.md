## 2. Method / tool (`scripts/loadtest/`)
**asyncio + httpx, not Locust.** Each week is a strict dependency chain (phase-a → phase-b, init-game → quarters, training poll). A scripted async runner replays it exactly, header for header, and stamps every request. Locust's user or rate model adds nothing for "N concurrent franchises each doing a full week". One process drives N concurrent sessions.

| File | Role | DB access |
|---|---|---|
| `common.py` | Hard guards: base URL must be exactly `https://gob-simplified-staging.up.railway.app`; DB must be `gob-staging`; writes need process `GOB_DB_ACCESS=write`. Tagging helpers | – |
| `seed.py --n N` | Inserts tagged users (`loadtest+<n>@example.com`, username `loadtest_<n>`, `loadtest:true`, onboarding complete; **staging is alpha mode, so API signup needs an access code**). Each user then logs in via the real `/api/auth/login` and creates a franchise via the real `select-team`. The franchise is stamped `loadtest_name="LOADTEST-<n>"`, because the API has no name field. Paces logins under the 10/min auth limit | write |
| `run.py` | The runner. `--users N --weeks W --mix 0.7` or `--plan sim,played,…`; `--turn-think` adds a per-turn delay for animation (0 in every run so far = worst case). Writes `reports/loadtest/<run>/requests.jsonl` (epoch start/end, latency, status per request), `weeks.jsonl` and `summary.json` | none (HTTP only) |
| `ramp.py` | Phase 2 steps and stop rules (not run) | none |
| `jobwatch.py` | Read-only job-doc poller behind the start-cpu-sims breakdown (§3a) | read |
| `cleanup.py [--yes]` | Removes only franchises owned by a tagged user **and** stamped LOADTEST (dry run by default). See below | write |
| `feeds.py snapshot / restore [--yes]` | Protects the shared feeds (§4) | read / write |

## 3a. Where start-cpu-sims' time goes (no app change)
**Method:** 1 fresh tagged franchise. Three sim weeks (weeks 4–6, 12:00:13–12:04:04Z, no deploy), with `scripts/loadtest/jobwatch.py` polling the franchise's `cpu_sim_jobs.<week>` doc once a second (read-only).
- The app persists that doc at known points: all matchups → `running` right before the pool; every 10 completed games during the persist loop (`CPU_SIM_JOB_HEARTBEAT_GAMES`); and `completed_at` at the end.
- Offsets below are seconds after the client sent start-cpu-sims. Server times come from Railway's clock and client times from mine, both NTP-synced (skew under ~0.5 s).

| Week | Request | Pre-pool (to `running`) | Pool end (first 10 persisted, minus ~2.3 s) | Persist loop (63 games) | Post | Quarters (all during the pool) |
|---|---|---|---|---|---|---|
| 4 | 51.7 s | 1.2 s | ≈ 36 s | ≈ 14.4 s (10 → 63 in 14.1 s) | ~0 | 3.9 / 4.2 / 4.2 / 5.0 s |
| 5 | 49.0 s | 1.1 s | ≈ 34 s | ≈ 13.3 s | ~0 | 3.7 / 4.5 / 4.2 / 4.9 s |
| 6 | 46.3 s | 1.8 s | ≈ 33 s | ≈ 12.9 s | ~0 | 3.4 / 3.5 / 4.5 / 4.8 s |

**What each segment is, from the code** (`franchise_routes._complete_week_finish_cpu_and_persist`; `utils/cpu_week_pool.py`):
1. **Pre-pool (~3%):**
   - `ensure_franchise_identities`
   - job build and persist
   - an FTD cache read
   - one `db.games.find_one` per matchup (63)
   - marking all matchups `running`
2. **Pool (~70%):** `simulate_cpu_week_pooled` → a **spawn** `ProcessPoolExecutor` with 8 workers.
   - Each worker is a fresh interpreter. It imports `BackEnd.api.franchise_routes`, which takes **0.8–1.7 s locally** as a proxy on an M4 Pro, and builds its own MongoClient.
   - Then, per game, `_run_franchise_cpu_full_simulation_core`:
     - 2 FTD reads (`_franchise_cpu_full_sim_ftd_doc`), which are Mongo reads
     - `prepare_ftd_for_new_game`
     - `GameManager` setup and lineups
     - four or more headless `simulate_quarter` calls (CPU)
     - `summarize_game_state`, which is serialization
   - **Workers write nothing.**
   - 63 games at 8 wide = 8 rounds, and ~34 s / 8 ≈ **4.2 s per round**. That's per-game sim time plus the per-game FTD reads, with spawn amortized into round 1.
3. **Persist loop (~28%):** after the pool, **sequentially in the web request's thread**, per game:
   - the `db.games` upsert
   - `stat_updater.finalize_game` (the FPD bulk write)
   - result records
   - `_finalize_team_attributes_for_game`
   - momentum updates
   - a job persist every 10 games

   That's **~0.23 s/game × 63 ≈ 14 s**. It's Mongo round trips plus Python in the web process; the per-kind split is in `[CPU-PERSIST-TIMING]`.
4. **Post (~0):** the job's `completed_at` equals the request end.

**Spawn vs per-game CPU vs Mongo vs serialization** (as asked): the job doc can't separate these inside the pool. The existing logs can, today, with no code change:
- **`[POOL-EFFICIENCY] cpu_week | jobs=63 workers=N | wall=…s worker_cpu=…s efficiency=…%`:**
  - `worker_cpu / jobs` is the true CPU per game.
  - `(1 − efficiency)` is the share of pool time spent not on CPU: spawn and import, Mongo reads in workers, round imbalance.
  - It also logs `[POOL-OVERLAP]` when the autotrain or practice-squad pools run at the same time.
- **`[CPU-WEEK-TIMING] … full_sim_block=…s (…s/full-game)`:** the pool wall.
- **`[CPU-PERSIST-TIMING] … persist_loop=…s`**, plus the sub-split: `games_write`, `finalize_game`, `records`, `team_attrs`, `momentum`.

**Instrumentation that would still be needed** for a full per-game split inside workers (app change, not done):
- stamp `t_imported`, `t_ftd_loaded`, `t_simulated` and `t_summarized` in `cpu_week_pool._worker`, and return them with the result
- log a per-week histogram of those phases, plus the result payload size (`summary` bytes, for serialization and IPC)
- have `_cpu_sim_mark_matchup_complete` stop overwriting `completed_at` in phase-b, so start-cpu-sims' own per-game completion times survive in the job doc

**Evidence on contention:**
- Quarters were **3.4–5.0 s while the pool ran** (separate processes), the same as week 1. So the pool doesn't slow the user's game.
- No quarter overlapped the persist loop in these runs (the user's game ends ~18 s in; the loop starts ~34 s in). So "the persist loop competes with the user's game for the GIL" is **not demonstrated**. At N>1 another user's quarters will overlap someone's persist loop, and Phase 2 will show it.

**Levers this points at (analysis only):**
- **Pool width:** 8 of 32 vCPUs. The pool is ~70% of the time and is round-bound (8 rounds). 16 workers → ~4 rounds (≈ –17 s), before accounting for Mongo read contention.
- **Persist loop:** ~28%, sequential per game, in the request thread. Batching those writes across games is where most of the remaining ~14 s is.

## 3b. The 2.5× environmental slowdown (11:13–11:50Z)
- **Same code** (`31c2a72` → `ac16ab1`: no BackEnd/config diff) and the same N=1, but **every** stage was ~2.5× slower in the first window: start-cpu-sims, cpu-train, the user's quarters and phase-b.
- **Uniform slowdown across CPU-bound and Mongo-bound stages** points to something box-wide or database-wide, rather than an app hot spot.
- **Candidates** (can't tell them apart without Jamie's graphs):
  - **production traffic on the shared Atlas MVP-Cluster** (07:13–07:50 ET, weekday morning)
  - other load on the staging service or host (another agent or user, e2e runs)
  - process state before the 11:54 redeploy
- **Consequence:** the audit's "hosted week ~115 s" and this report's 125 s are **not** a fixed property of the code. The same week is ~50 s on a quiet cluster. Staging-on-shared-Atlas measurements need the time of day recorded, and Phase 2 must run in a window whose baseline is re-measured at the start of the ramp.

## 5. Findings so far (evidence, not fixes)
1. **The CPU slate (`start-cpu-sims`) is the week's critical path, and it degrades with concurrency.**
   - 120–131 s at N=1, 158 s at N=2, with one uvicorn process on staging.
   - phase-b's server-side wait is 150 s. At roughly **N ≈ 3–5**, phase-b is likely to start returning **503 "CPU sims … still in progress"** to real users. That's the probable first failure mode, and Phase 2 will confirm it.
   - **Caveat:** the "N ≈ 3–5" estimate is from the **slow window**. In the fast window, start-cpu-sims is ~50 s at N=1, so the 150 s phase-b cliff sits at a higher N. Phase 2 must measure its own baseline at the start.

2. **The user's game slows at N=2.** simulate-quarter p95 went from 10 to 22 s in the slow window.
   - §3a shows the **pool itself doesn't** slow quarters (N=1, fast window: 3.4–5.0 s during the pool).
   - So the N=2 rise is more likely the other franchise's in-process work (its persist loop and request handling, same process and GIL) or the environment.
   - Phase 2 should separate these (not demonstrated yet).
3. **The training wait, cpu-train, is 44–54 s every week** and grows with N.
4. **A deploy mid-week is destructive:**
   - A develop merge redeployed staging at 11:13:18Z during a debug run.
   - Both in-flight requests (start-cpu-sims at 43 s, phase-b at 22 s) got **502**.
   - The killed process's claim stayed active until its 300 s staleness window passed, so the next phase-b waited 150 s and got **503**.
   - A real user in that window is stuck for ~5 min. On production, any deploy during play does this.
   - This also means **measurement runs must not span a deploy**. Other agents merge to develop constantly, and staging redeploys on each merge. Every run records the deployed commit before and after.
5. **`eog_band_log` grows fast:** ~16.9k docs for 2 franchises over ~10 weeks, and the API delete never removes them. That confirms the audit's orphan finding.
